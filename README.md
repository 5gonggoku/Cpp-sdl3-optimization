# SDL3 대량 오브젝트 시뮬레이션: 구조 설계와 측정 기반 최적화

적 최대 2만 개와 총알이 움직이는 2D 시뮬레이션입니다. 게임성이 아니라 **C++ 구조 설계와 측정 기반 최적화**를 보여 주려고 만들었습니다. 최적화 전 구현을 실행 옵션으로 남겨 두고, 단계마다 결과가 처음과 똑같은지 체크섬으로 비교했습니다.

- 언어/도구: C++17, SDL3, Dear ImGui, CMake, vcpkg, MSVC (Windows)
- 기간/인원: 1인, 약 1주일 (개발 기간 기준이며, 공개 저장소의 커밋은 아래 "커밋 이력 안내"처럼 정리해 올린 것입니다)

## AI 사용 범위

이 프로젝트는 Claude Code(AI 코딩 도구)와 함께 만들었습니다.

- **코드 설계와 작성**: C++ 코드의 설계와 작성은 직접 했습니다. 다만 `src/bench/`(벤치마크 CLI 옵션 파싱, 실행 루프, 환경 정보 수집)와 `tests/`(단위 테스트, 파서 퍼징)는 Claude Code가 작성했습니다. `src/data/`(JSON 파서, `ILoader<Key, Value>`, `DataManager`)는 C#에서 써 본 `ILoader` 기반 JSON 역직렬화·데이터 테이블 관리 구조를 C++로 옮겨 보고 싶어서 Claude Code의 도움을 받아 함께 작성했습니다.
- **개발 환경과 빌드 설정**: SDL3 설치는 직접 했고, Dear ImGui 연동과 CMake, vcpkg 설정(MSVC 빌드 환경에 맞춘 부분 포함)은 Claude Code가 작성했습니다.
- **빌드, 테스트 실행, 측정, 수치 정리, 문서 기록, 커밋**: Claude Code로 진행했습니다.
- **README**: 초안은 Claude Code가 작성했고, 작성자가 검토하며 수정했습니다.

### 커밋 이력 안내

이 공개 저장소의 커밋 이력은 개발 중 전체 기록이 아니라 정리해서 올린 것입니다. 그래서 커밋 수가 적고, 본문에서 언급하는 `git revert` 같은 작업은 공개본에 남아 있지 않습니다. 커밋은 Claude Code로 진행했습니다.

## 성능 요약

**측정 조건**: Release 빌드(x64), 적 1만 개, 최초 구현과 같은 값의 옛 데이터(`data/legacy_v1`, 적 1종), 같은 세션에서 버전을 번갈아 15번씩 실행한 중앙값입니다. 고정 시드(12345), 측정 3600틱(워밍업 300틱), VSync 끔, 렌더링 없음. 환경은 AMD Ryzen 5 7500F, RAM 32GB, Windows 11(10.0.26200), MSVC 19.43입니다.

**체크섬**은 시뮬레이션이 끝난 시점의 상태(플레이어·적·총알 위치, 개수, 누적 명중 수 등)를 해시한 값입니다. 최적화 전후 값이 같으면 결과가 동일하다는 뜻이고, 이 표의 모든 버전이 같습니다(`8fff949560f7460e`). 아래 "단계별 요점"의 새 기본 데이터(적 3종)는 체크섬이 `577572ee1c90351a`이며, 풀·그리드·floor 제거 전후가 모두 같습니다.

**"틱 평균"**은 벤치 한 번이 잰 3600틱의 틱당 평균 시간이고, 표의 값은 이 벤치를 15번 돌린 중앙값입니다. "v3 naive 옵션"은 그리드 코드가 들어간 v3에서 충돌 방식만 `--collision=naive`(옛 전수 비교)로 돌린 것이라 v2와 비슷하게 나옵니다.

| 버전 | 틱 평균 (ms) | v1 대비 | 틱당 충돌 검사 | 틱당 힙 할당 |
|---|---|---|---|---|
| v1 naive (기준) | 0.2009 | - | 약 15만 | 1.881 |
| v1.5 데이터 기반(JSON) | 0.2683 | +33.5% | 약 15만 | 1.881 |
| v2 오브젝트 풀 | 0.2249 | +12.0% | 약 15만 | 0 |
| v3 naive 옵션 | 0.2253 | +12.1% | 약 15만 | 0 |
| v3 균일 그리드 | 0.1061 | -47.2% | 16.8 | 0 |
| 현재 | 0.0996 | -50.4% | 16.8 | 0 |

값은 `docs/perf/portfolio_summary.csv`, 근거 행은 `docs/perf/bench_selected.csv`에 있습니다.

### 단계별 요점

위 표는 옛 데이터(적 1종) 15라운드이고, 아래 표는 **새 기본 데이터**(적 3종, 12:6:2, 적 1만 개)라서 같은 항목도 힙 할당·충돌 검사 절대값과 감소율이 다릅니다. 20% 이상의 큰 차이는 3회 중앙값으로, 20% 미만의 작은 차이는 15라운드로 판정했고 줄마다 횟수를 적었습니다. 20% 경계 근처의 값은 15라운드 값을 우선합니다.

| 단계 (새 기본 데이터) | 틱 평균 (ms) 전 → 후 | 틱 변화 | 재구성 변화 | 측정 |
|---|---|---|---|---|
| 오브젝트 풀 | 0.2308 → 0.1817 | -21.3% | - | 3회 중앙값 |
| 균일 그리드 | 0.1880 → 0.1046 | -44.4% | - | 3회 중앙값 |
| 위치 복사 실험(되돌림) | 0.1025 → 0.1164 | +13.6% | -7.5% | 15라운드 |
| `std::floor` 제거 | 0.1101 → 0.1018 | -7.5% | -12.7% | 15라운드 |

- **오브젝트 풀**: 매 틱 `new/delete`하던 적과 총알을 풀에서 빌려 쓰게 해 힙 할당을 1.591회에서 0회로 줄였습니다(JSON 데이터 기반 버전 대비). 새 기본 데이터의 -21.3%는 3회만 측정했고 20% 경계 근처라 참고값으로 두고, 대표값은 위 표의 15라운드 값인 -16.2%(0.2683 → 0.2249, 힙 할당 1.881 → 0)입니다.
- **균일 그리드**: 충돌 검사가 120,346.8회에서 87.0회(-99.9%)로 줄었지만 틱은 -44.4%만 줄었습니다(풀 버전 대비). 위 표(옛 데이터, 15라운드)에서는 v1 대비 -47.2%, 충돌 검사 150,244.8 → 16.8입니다. 구간별로 나눠 재 보니 충돌 구간의 약 83%가 매 틱 그리드를 다시 만드는 비용이었습니다(새 기본 데이터 3회 중앙값: 충돌 0.0607 ms 중 그리드 빌드 0.0502 ms).
- **틀린 가설**: JSON 데이터화 후 틱이 느려진 원인(옛 데이터, v1 대비 15라운드 +31.6%, 위 표의 같은 구간 +33.5%는 다른 세션 값)을 포인터 간접 참조, 객체 크기, 명령 수, 필드 배치로 의심해 하나씩 실험했고 모두 기각했습니다. 풀 도입 뒤에도 v1보다 약 +10%가 남았고 원인은 확정하지 못했습니다. 독립 세션 3개(각 15라운드)에서 v2 풀은 +10.1·+9.1·+10.0%, v3 naive 옵션은 +9.9·+10.4·+9.8%였고, 같은 실행 파일을 두 번 돌린 대조군(A/A)은 -0.4·+0.1·+0.1%였습니다. 위 표의 +12%와 별도 세션의 +7.2%까지 보면 세션마다 +7~12%로 흔들려 한 값으로 단정하지 않습니다.
- **되돌린 실험**: 적 위치를 연속 배열에 한 번 더 쓰는 방식은 재구성이 -7.5% 줄었지만 틱이 +13.6% 늘어 `git revert`로 되돌렸습니다(같은 실행 파일 대조군 A/A는 틱 -1.2%).
- **비용 분해 후 수정**: 재구성 안에서 채우기, floor와 clamp, 개수 세기 비용을 나눠 잰 뒤 `std::floor`를 없애는 두 줄 수정으로 재구성 -12.7%, 틱 -7.5%를 얻었습니다. 분해용 실험 중 채우기와 개수 세기를 뺀 탐침(probe)은 계산을 일부러 빼서 체크섬이 달라지므로 개선으로 세지 않았습니다. 위 표의 -6.1%(v3 균일 그리드 0.1061 → 현재 0.0996, 옛 데이터)와는 데이터와 기준 빌드가 다르고, "재구성 -7.5%"(되돌린 실험)와 숫자만 같을 뿐 다른 측정입니다.

## 측정 규칙

- 수치는 Release 빌드에서만 기록하고, 고정 시드와 고정 틱 수로 렌더링 없이 시뮬레이션만 측정합니다.
- 비교할 버전은 같은 세션에서 번갈아 실행하고, 최적화 전후 체크섬이 다르면 개선으로 인정하지 않습니다.
- 20% 이상의 큰 차이는 3회 중앙값으로 판정합니다(풀·그리드 구간의 3회 값이 이 경우). 20% 경계 근처 값은 15라운드 값을 우선합니다.
- 20% 미만의 작은 차이는 편차와 겹치므로 15번 이상 반복하고, 같은 실행 파일을 두 번 돌린 대조군(A/A)의 오차보다 큰지 확인합니다. 3회로는 이 크기의 차이를 판정하지 못했습니다(3회로 "차이 없음"이라 적었던 +7.2% 잔여 회귀가 15라운드에서 실재로 확인됨).

## 구조

src/main.cpp, src/render/   창 모드 (SDL3, ImGui는 여기에만 있음)
src/bench/                  창 없이 같은 World를 돌려 CSV에 기록하는 벤치 모드
src/gameplay/               World, Player, Enemy, Bullet (SDL을 모르는 정적 라이브러리)
src/memory/                 Pool<T> 오브젝트 풀, 할당 횟수 계측
src/physics/                SpatialGrid 균일 그리드 충돌
src/data/                   직접 만든 JSON 파서, ILoader<Key, Value>, DataManager
tests/                      단위 테스트와 파서 퍼징
data/                       적 종류와 웨이브 JSON (기본, legacy_v1, demo_timed)
docs/perf/                  측정 결과 CSV

## 빌드와 실행

x64용 MSVC 환경(`vcvars64.bat` 실행 후 또는 x64 Native Tools Command Prompt)에서 실행합니다. `VCPKG_ROOT`가 vcpkg 경로를 가리켜야 합니다.

cmake --preset x64-release
cmake --build out/build/x64-release
out\build\x64-release\game.exe            (창 모드)
out\build\x64-release\game.exe --bench    (벤치마크 모드)

- `--collision=naive|grid`: 충돌 방식 선택(기본 grid, naive는 최적화 전 구현)
- `--enemies=N`, `--ticks=N`, `--data=<폴더>`: 시나리오 조정
- 벤치는 프로젝트 루트에서 실행합니다.

## 테스트와 안정성

ctest --test-dir out/build/x64-release

- 단위 테스트 4종: `json_tests`, `world_tests`, `pool_tests`, `grid_tests`
- `x64-asan` 프리셋으로 메모리 오류 검사(AddressSanitizer)와 JSON 파서 퍼징을 수행했습니다. 결과는 `docs/perf/stability_summary.csv`에 있으며, 이 값들은 프로젝트 기록에서 옮긴 것이고 퍼징은 약 5분 분량이라 "버그가 없다"는 증명은 아닙니다.

## 측정 CSV 읽기

python -I scripts/analyze_bench_csv.py
python -I scripts/analyze_bench_csv.py --label gap

`docs/perf/bench_selected.csv`의 `label`별 중앙값을 표로 보여 줍니다. `source_line`은 개발 중 사용한 원본 측정 파일의 줄 번호이며, 원본 파일은 이 저장소에 포함되어 있지 않습니다.
